# 新用户体验与推广设计

> 本页保留不同阶段的设计记录。当前用户入口、版本、商店状态与能力边界以 [安装指南](./GETTING_STARTED.md)和 [1.0 说明](./RELEASE_1_0.md)为准；后文「尚在审核 / 待发布」描述的是各自记录日期，不能用作当前发布证明。

## 当前规范：扩展优先的完整产品流程（2026-10-23）

新的规范见 [桌面产品体验规范](./DESKTOP_PRODUCT.md)。它取代下方历史记录中「不建设安装器」与「普通用户经终端安装服务」的阶段性取舍；保留历史不是继续使用旧入口。

唯一默认路径：**Chrome 商店安装扩展 → 基础阅读立即可用 → 按需开启 AI / 同步 → 官网 `download.html` → 安装打开桌面端 → 自动准备与发现候选 → 回扩展确认连接 → 完成一条真实回答或笔记同步 → 回到阅读。**

- 官网主 CTA 是安装扩展；桌面下载是给已安装用户的后续入口，不将用户再次送回商店。
- 下载页按系统和架构展示真实可用状态。当前没有公开签名包，必须明确写开发预览；不得放虚假的下载按钮或猜测架构。普通用户不需要从 GitHub 附件列表选包。
- 桌面首启负责自动准备本地服务和受限发现。发现只检查已知入口 / 已登记位置等元信息，不自动读取正文、授权、登录或调用收费模型。
- 首启是有进度、能跳过、可继续的任务流程；完成后进入日常状态，不永久显示安装清单。服务进程正常不等于完整连接完成。
- 基础批注与导出一直可用。AI、笔记同步分别配置、验证、失败恢复，不能互相假定通过。
- Node/npm、配对码和旧 LaunchAgent 放入高级兼容路径；已有用户不必删除配置或数据。

网站 / README / 引导文案不作为已发布证明。桌面签名公证、Windows 实机验收和扩展新权限仍是独立发布关卡。

## 判断

截至 2026-10-17，旧入口适合熟悉命令行的维护者，不适合直接承担面向普通读者的推广转化。证据来自 README、首次安装选项页、扩展图标行为和实际代码路径，尚未做真实新用户可用性测试。

主要问题：README 在安装说明前放了约 200 行愿景和架构；统一要求 Node.js 让用户以为基础批注也依赖服务；三个 ZIP 没有清晰的选择规则；欢迎页从 npm 命令开始；未配对图标直接打开连接页；服务离线与插件不可用的表达混在一起；连接成功没有形成清晰的下一步。

## 用户与首要承诺

第一批核心用户：经常阅读网页、希望把原文和判断带回 Obsidian / Markdown 的读者与研究者。会配置模型的技术用户是进阶人群，不是所有安装者的默认画像。

首要承诺：**在原文旁记下想法，把阅读记录带回自己的笔记。** 首次成功定义为「一条带来源的批注能恢复、能导出」。不以配对成功、打开设置或输入 API key 作为激活。

## 信息与使用路径

| 阶段 | 用户需要回答的问题 | 入口和完成标志 |
| --- | --- | --- |
| 看懂 | 它替我解决什么问题？ | 首屏一句话 + 三个真实用途 + 实际操作画面 |
| 安装 | 下载哪个？要不要敲命令？ | 只安装 Chrome 包；安装后能在普通文章看到工具条 |
| 第一次成功 | 我要先做什么？ | 练习文章 → 批注 → 刷新恢复 → 下载 Markdown |
| 形成日常使用 | 如何回看和带走记录？ | 固定图标、双向定位、定期导出、选择同步目录 |
| 增加能力 | 想要笔记同步或 AI？ | 自选展开连接引导；配对后分别验证同步或一条 AI 回答 |
| 个人上下文 | 如何关联自己的笔记？ | 已有阅读价值后，再介绍本地 agent、授权目录和来源核对 |

README 是产品发布首页，承担价值理解、体验展示、信任建立和安装选择；欢迎页承担第一次行动；完整指南承担详细步骤与排障；开发文档承载编译、架构与发布流程。各页面共用同一套术语和文件命名解释。

### README 的产品发布结构

首屏承诺为「把阅读，变成可复用的上下文」，面向深度阅读者介绍网页、AI 与个人笔记之间的工作流。主入口是下载扩展与开始使用，不用练习页或配置命令代替产品价值。

真实界面先展示原位批注与侧栏同步，再依次介绍上下文追问、可迁移的阅读笔记、按授权接入个人上下文。安装说明压缩成三步，终端操作留在完整指南；能力前提、数据边界和当前商店审核状态仍要清晰可见。中英文页面保持相同的产品叙事，不把开发版截图标成已发行的界面。

## 下一阶段：先完善产品呈现与首次使用

按当前产品取舍，暂不建设可视化配置安装器。优先完善产品首页、真实界面展示、发行入口和现有安装指南，验证用户能否理解价值并独立完成一次批注与导出。

文案不能消除 Node.js、终端、配对和模型配置的实际成本。推广中明确区分「无需配置的批注导出」与「需要本地环境的 AI / 笔记同步」，不承诺非技术用户几分钟就能配置完整个人 agent 工作流。未来若重新评估本地安装器，需要另行规划各系统打包、签名、干净机器验证与升级机制，不把未经验证的脚本称为“一键安装”。

面向海外推广还需要英文界面、英文演示和相应商店文案；只有英文 README 并不等于完整英文体验。当前界面主要为中文，先围绕中文阅读与 Obsidian 用户验证，再逐步扩大语言覆盖。

## 推广节奏

1. **先验证首次成功。** 找 5–8 位没有使用过 ContextFlow 的目标读者，给同一个公开入口，让他们独立完成批注和导出。记录卡点，先解决共性障碍。
2. **再发布真实演示。** 录制一段从安装到第一条批注与 Markdown 文件的短演示；另录一段 AI / 笔记关联进阶演示，避免把终端步骤剪掉后宣称开箱即用。
3. **按场景介绍。** 面向 Obsidian / Markdown 社区讲阅读记录如何进入自己的笔记；面向研究者讲保留原文、证据和判断；面向 agent 用户再展示个人上下文。每个入口都回到同一份安装指南与练习文章。
4. **最后扩大覆盖。** 商店通过后将主入口切到商店，简化解压教程为备用路径。先确认支持与排障能承接真实用户，再增加宣传渠道。

## 验收目标

以下是待验证的目标，不是已测得的成绩：首次看到首页能解释核心用途；无需维护者协助完成安装；首次会话完成批注、刷新恢复和导出；遇到未配对或服务未启动时知道下一步；配置失败不会让用户误以为批注丢失。

先用人工可用性测试和自愿反馈收集这些信号。当前不添加遥测；若以后需要产品分析，单独设计告知、数据最小化和选择机制。

## 安装目录误操作修复：2026-10-19

用户通过已安装的商店版 0.3.1 连接页执行 `npm ci`，在主目录安装了无关项目的依赖并遇到 E404。已读取实际安装的 0.3.1 页面确认：它仅写「在项目目录」，未明确下载哪个配套包、如何进入目录或检查项目。这是安装引导缺陷，不能仅以「用户执行目录不对」结案。

本地待发布的连接页拆分下载、进入目录、目录确认、安装启动与配对；说明 Chrome 扩展不会自动安装服务。复制的安装、配对与撤销命令都先校验当前项目，失败不执行 npm。新终端需要再次进入目录。用户指南与后续 companion 包说明保持一致。

验收增加错误目录、缺失或损坏的 package.json、无关项目、路径含空格、安装失败不继续启动，以及实际浏览器复制内容和窄屏展示。源码修改不会改变已安装的 0.3.1 页面；替换该页面需要另行打包并发布商店更新，不覆盖既有发行包。

公开商店入口已验证：现行为 0.3.1。README、用户指南和支持站点源码改为商店安装优先；0.3.1 保留兼容步骤，0.3.2 不冒充已发布。

待发布的 0.3.2 同时修复：

- 点击同步前先补发待发送记录，避免刚完成批注就同步时遗漏；关闭终端后的恢复路径与常驻服务边界清楚说明。

`test/onboarding-browser.test.mjs` 使用全新解压的 companion ZIP、隔离配置和浏览器资料，执行设置页实际复制的启动命令，然后验证配对、模型配置、真实 Markdown 同步和服务重启。模型端使用隔离模拟服务，不把它称为真实计费模型兼容性验证。原有浏览器回归继续覆盖独立存储、刷新恢复、撤销与离线导出。

边界：验收环境为本机 macOS 与隔离 Chromium；Windows / Linux 的说明和命令前提已补齐，但不声称完成了这两个系统的干净机器验收。没有建设可视化安装器；Node.js、网络、用户的模型凭证和笔记软件仍是相应能力的前提。
