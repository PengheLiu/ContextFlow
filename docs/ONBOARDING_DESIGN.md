# 新用户体验与推广设计

## 判断

截至 2026-10-17，旧入口适合熟悉命令行的维护者，不适合直接承担面向普通读者的推广转化。证据来自 README、首次安装选项页、扩展图标行为和实际代码路径，尚未做真实新用户可用性测试。

主要问题：README 在安装说明前放了约 200 行愿景和架构；统一要求 Node.js 让用户以为基础批注也依赖服务；三个 ZIP 没有清晰的选择规则；欢迎页从 npm 命令开始；未配对图标直接打开连接页；服务离线与插件不可用的表达混在一起；连接成功没有形成清晰的下一步。

## 用户与首要承诺

第一批核心用户：经常阅读网页、希望把原文和判断带回 Obsidian / Markdown 的读者与研究者。会配置模型的技术用户是进阶人群，不是所有安装者的默认画像。

首要承诺：**在原文旁记下想法，把阅读记录带回自己的笔记。** 首次成功定义为「一条带来源的批注能恢复、能导出」。不以配对成功、打开设置或输入 API key 作为激活。

## 信息与使用路径

| 阶段 | 用户需要回答的问题 | 入口和完成标志 |
| --- | --- | --- |
| 看懂 | 它替我解决什么问题？ | 首屏一句话 + 三个真实用途 + 实际操作画面 |
| 安装 | 下载哪个？要不要敲命令？ | 只安装 Chrome 包；安装后能在普通文章看到工具条 |
| 第一次成功 | 我要先做什么？ | 练习文章 → 批注 → 刷新恢复 → 下载 Markdown |
| 形成日常使用 | 如何回看和带走记录？ | 固定图标、双向定位、定期导出、选择同步目录 |
| 增加能力 | 想要笔记同步或 AI？ | 自选展开连接引导；配对后分别验证同步或一条 AI 回答 |
| 个人上下文 | 如何关联自己的笔记？ | 已有阅读价值后，再介绍本地 agent、授权目录和来源核对 |

README 承担了解和选择；欢迎页承担第一次行动；完整指南承担详细步骤与排障；开发文档承载编译、架构与发布流程。各页面共用同一套术语和文件命名解释。

## 下一阶段：真正降低 AI 安装门槛

文案不能消除 Node.js、终端、配对和模型配置的实际成本。面向更广泛用户前，最高优先级是签名的本地配套安装器：安装 / 启动 / 卸载可视化，明确的连接状态，浏览器引导配对，保留撤销机制。macOS 与 Windows 需要各自打包、签名、干净机器验证和升级机制，不应把一个未经验证的 shell 脚本称为“一键安装”。

在该能力完成前，推广中明确区分「无需配置的批注导出」与「需要本地环境的 AI / 笔记同步」。不承诺非技术用户几分钟就能配置完整个人 agent 工作流。

面向海外推广还需要英文界面、英文演示和相应商店文案；只有英文 README 并不等于完整英文体验。当前界面主要为中文，先围绕中文阅读与 Obsidian 用户验证，再逐步扩大语言覆盖。

## 推广节奏

1. **先验证首次成功。** 找 5–8 位没有使用过 ContextFlow 的目标读者，给同一个公开入口，让他们独立完成批注和导出。记录卡点，先解决共性障碍。
2. **再发布真实演示。** 录制一段从安装到第一条批注与 Markdown 文件的短演示；另录一段 AI / 笔记关联进阶演示，避免把终端步骤剪掉后宣称开箱即用。
3. **按场景介绍。** 面向 Obsidian / Markdown 社区讲阅读记录如何进入自己的笔记；面向研究者讲保留原文、证据和判断；面向 agent 用户再展示个人上下文。每个入口都回到同一份安装指南与练习文章。
4. **最后扩大覆盖。** 商店通过后将主入口切到商店，简化解压教程为备用路径。先确认支持与排障能承接真实用户，再增加宣传渠道。

## 验收目标

以下是待验证的目标，不是已测得的成绩：首次看到首页能解释核心用途；无需维护者协助完成安装；首次会话完成批注、刷新恢复和导出；遇到未配对或服务未启动时知道下一步；配置失败不会让用户误以为批注丢失。

先用人工可用性测试和自愿反馈收集这些信号。当前不添加遥测；若以后需要产品分析，单独设计告知、数据最小化和选择机制。
