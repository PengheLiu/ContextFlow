# ContextFlow 完整产品体验规范

本规范统一官网、README、Chrome 扩展和 macOS / Windows 桌面端的产品体验。它是实现与验收依据，不是已上线证明；实际公开可用范围以官网下载页与已安装版本为准。

## 1. 一个产品，两个有分工的界面

ContextFlow 帮助读者在原文旁形成理解，再把理解带回自己的笔记。用户不应为了这个目标，先学会 Node、服务端口、Native Messaging 或 CLI 配对。

- **扩展是阅读现场。** 批注、贴图、解释、翻译、速览、阅读库、导出与主动同步都从这里发生。
- **桌面端连接自己的工具。** 管理本机运行、模型 / Agent、笔记位置、权限、更新与问题恢复，不复制第二套阅读器。
- **官网承接安装。** 第一次访问先安装扩展；已安装用户从专门的桌面下载页继续，不在 GitHub 附件列表做文件辨认题。

基础阅读不依赖桌面端。安装顺序明确，不等于强迫每个用户安装两个应用。

## 2. 唯一默认主流程

1. 从 Chrome 商店安装扩展；刷新文章，基础批注即可开始。
2. 用户需要 AI 或同步时，从扩展的连接入口进入官网 `download.html`。
3. 确认系统、芯片架构和真实发布状态，安装打开桌面端。
4. 桌面端自动准备本地运行和浏览器桥接，并发现支持的工具候选。
5. 回扩展「连接桌面端」，在桌面弹窗核对来源后「允许连接」。
6. 确认自己要使用的工具与笔记目的地；AI 和同步可以独立跳过。
7. 回文章完成一条真实回答，或点击「同步」写入一份真实笔记。

普通流程不要求终端命令或手工复制配对码。模型自身的 API key 仍由用户提供。未安装桌面端、未配置 AI、没有笔记软件，都不是基础阅读失败。

### 各触点只回答当前问题

| 触点 | 当前任务 | 主要下一步 |
| --- | --- | --- |
| 官网首页 / README | 理解价值、安装扩展 | Chrome 商店 |
| 扩展欢迎页 | 第一条批注；按需增加能力 | 回到阅读 / 官网桌面页 |

## 3. 首次启动：自动准备，明确确认

启动应用自动准备服务，正常状态不把“启动 / 重启 / 停止服务”作为首屏主操作。旧服务冲突不能靠强杀未知进程解决；确认归属、保留数据，再按提示接管。

发现任务相互独立：一个工具检测超时，不阻塞其他候选展示或基础阅读；每项有准备中、发现结果、未发现、需处理和重新检测。首次引导可跳过并从原状态继续，不把已完成步骤反复呈现。

发现结果是候选，不是配置完成：

- Agent：检查已知程序入口、安装信息与版本，不启动生成任务；“已发现”不表示登录或模型可用。
- 笔记：检查应用已登记的 Vault / 配置路径，以及用户已保存的位置；不遍历整块磁盘、不扫描正文、不自动导入。
- 通用目录：可以提供明确标注的新建默认位置建议，不能把“Documents 存在”称为发现了用户的知识库。
- 未发现：正常空状态，提供选择程序 / 目录或稍后设置，不用红色失败描述未安装的可选工具。

用户确认后才保存候选、授权读取范围或写入目标。检测不自动发起付费测试；连接测试显示用途与费用前提。读笔记与写笔记是两种权限，不绑定授权整个磁盘。

## 4. 完成态按能力，不按端口计算

状态必须来自同一份实际运行配置和有效测试记录：

- **应用准备好：** 本机服务和桥接正常，仅表示桌面运行能力。
- **浏览器已连接：** 当前扩展安装实例已授权，不能由本机安装了 Chrome 推断。
- **AI 已验证：** 当前选定模型 / Agent 的匹配配置经过主动连接测试；程序存在或字段非空不算通过。
- **笔记位置已确认：** 目的地与写入范围已保存；不等于真实同步成功。
- **真实使用成功：** 文章得到回答，或目标实际写入当前文章的记录，才形成对应能力的闭环。

首次引导不强迫同时配置 AI 与笔记，但必须明确用户已经完成什么、跳过什么、以后从哪里继续。“回到阅读”不需要等所有可选能力全绿；它不能同时暗示未配置的 AI 已经就绪。

## 5. 日常界面不是开发控制台

首次引导完成后，首页只呈现当前选择、状态和需要处理的下一步；不永久展示安装教程或把所有底层能力堆成同权重按钮。

工具配置围绕对象组织：一个 Agent 的发现、程序路径、权限、测试结果位于同一上下文；笔记位置的选择、保存、验证也在同一上下文。不在页顶放四个与表单脱离的选择按钮，再让用户寻找对应字段。

界面共用品牌、图标、字号、间距与状态语义；保留足够信息密度，不用大幅英语标语替代操作。主操作唯一，辅助操作降级；错误首先说明影响，再提供可执行修复。草稿不被后台状态刷新覆盖，长任务不反复闪烁或抢焦点。键盘与减少动态效果偏好需可用。

macOS 菜单栏与 Windows 托盘符合各自系统行为：关闭窗口可隐藏，退出应用才停止服务。登录启动由用户选择，首次安装不能未经说明改变系统启动行为。AI 任务运行时，退出、更新与恢复都有明确处理，不默默重放付费请求。

## 6. 发布与下载不可虚构

官网桌面页是统一公开入口；README 和扩展不维护不同的猜测下载链接。每个系统 / 架构独立列出可用状态，无法确定用户架构时要求确认，不凭浏览器 UA 猜芯片。

独立下载与签名发行分开记录。官网直接称“桌面客户端”，不使用“预览版”标签；实际提供未签名包时，必须清楚说明缺少 Developer ID / Apple 公证、系统可能拦截，以及已验证的系统和架构，不生成会 404 的下载链接。SHA 不是发布者身份认证，不把 EXE 构建成功当作 Windows 实机通过。更高质量的签名发行仍需签名 / 公证（适用时）、对应架构安装运行、升级与退出验收。

扩展新连接权限也必须经过独立发行。老商店版缺少入口时，保留记录并解释兼容范围，不以卸载数据来换更新。公开文案不把本地源码预览叫作所有用户已安装的正式能力。

高级 CLI 兼容路径保留，但不与普通桌面流程同屏展开。安装包内置运行环境的目标不能导致删掉已有用户的数据或强制迁移。桌面加密配置与旧 CLI 回退边界需事先说明。

## 7. 数据保护是产品体验的一部分

浏览器完整备份与桌面本机恢复点是不同范围。恢复点不包含浏览器离线记录、外部 Markdown / Vault / 思源文档或浏览器授权；不能宣传为“撤销整个系统”。原始日志可能含隐私，反馈默认使用白名单脱敏报告。

模型、Agent、第三方笔记软件的账号与额度由用户提供。本地优先不等于 AI 完全离线。自动发现不扩大权限，Full 权限需单独理解和确认，不为通过首次测试诱导开启。

## 8. 端到端验收门槛

从扩展商店的入口开始，分别验证干净系统与已有用户的状态：

- 不会再次要求安装已经装好的扩展，也不会默认进入 npm / GitHub 附件列表。
- 系统架构无法确定、没有公开包或系统安全阻止时，不出现假成功和假下载。
- 应用打开自动准备；慢 / 缺失工具不会阻塞整个引导；发现候选不会自动授权。
- 浏览器只确认自己的申请；拒绝、取消、撤销、重新连接都有保留数据的明确结果。
- AI、Agent、笔记目的地单独验收；一次真实回答和一次真实文件落盘分别留有证据。
- 改设置后，扩展与桌面状态一致；未保存草稿和过期测试不误导用户。
- 关闭窗口、退出、重新打开、登录启动、睡眠恢复可解释且可重复。
- 安装更新 / 回退保留数据边界；Windows 需 Windows 实机，Mac 各架构分别验收。

先用目标读者独立走查收集卡点，不默默新增遥测。评估的是能否独立完成工作，而不是是否把所有设置页面点开过。
